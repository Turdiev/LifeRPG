## Стек

Весь проект на TypeScript: React-клиент, API на Hono и PostgreSQL через Drizzle, с общими схемами и доменной логикой в одном монорепозитории. Документ реализует [PRD](https://claude.ai/artifact/21vaibhviKLo993vcq5Gxf) и [UX/UI спецификацию](https://claude.ai/artifact/XYiwTTDJGae7wsKFH85MG6); точные версии библиотек фиксируются в `package.json` при создании проекта.

## Архитектура

Классическая трёхзвенная схема: PWA в браузере ходит в REST API, API — единственный, кто работает с базой и почтой; доменная логика лежит в общем пакете и выполняется и на сервере, и на клиенте.

&#91;embedded content: архитектура · клиент, API, внешние сервисы\]

- **Клиент** — одностраничное приложение (SPA). Сервис-воркер кэширует оболочку приложения, TanStack Query держит данные и очередь изменений.
- **API** — слои строго сверху вниз: маршруты (HTTP и валидация) → сервисы (транзакции, права доступа) → доменная логика (чистые функции) → репозитории на Drizzle.
- **Общая доменная логика** (`packages/domain`) считает прогресс и каскады статусов. Сервер применяет её как источник истины, клиент — для мгновенных оптимистичных обновлений.
- **Один Worker — один адрес.** Cloudflare Worker отдаёт собранный клиент как статические файлы и обрабатывает `/api/*`. Клиент и API живут на одном адресе, поэтому cookie сессии обычные, first-party, и свой домен для них не нужен.
- **База в ЕС.** Neon во Франкфурте; Worker выполняется на ближайшем узле Cloudflare, а Hyperdrive держит пул соединений к базе, чтобы запрос не открывал новое соединение.
- **Ограничение Workers:** 10 мс процессорного времени на запрос в бесплатном плане. Ожидание базы и сети сюда не входит, а пересчёт дерева до 2 000 узлов укладывается с запасом.

│     ├─ wrangler.jsonc     # статика из apps/web/dist, маршруты /api/*, Hyperdrive
│     └─ src/

Пакет `domain` не знает ни о базе, ни о HTTP, ни о React: на вход — массив узлов дерева, на выход — новые статусы и прогресс. Поэтому он покрывается самыми быстрыми и подробными тестами.

## Модель данных

Все четыре уровня квестов живут в одной таблице `quests`; статус хранится у каждого узла, а прогресс никогда не хранится и считается при чтении.

```sql
CREATE TYPE quest_kind   AS ENUM ('line', 'chapter', 'quest', 'step');
CREATE TYPE quest_status AS ENUM ('open', 'done', 'paused', 'cancelled');

CREATE TABLE quests (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id      text NOT NULL REFERENCES "user"(id) ON DELETE CASCADE,
  line_id      uuid NOT NULL,              -- корень дерева; у линии равен её id
  parent_id    uuid REFERENCES quests(id) ON DELETE CASCADE,
  kind         quest_kind   NOT NULL,
  status       quest_status NOT NULL DEFAULT 'open',
  title        varchar(120) NOT NULL,
  description  text,
  deadline     date,
  position     text NOT NULL,              -- дробный индекс порядка среди «братьев»
  completed_at timestamptz,
  created_at   timestamptz NOT NULL DEFAULT now(),
  updated_at   timestamptz NOT NULL DEFAULT now(),
  CHECK ((kind = 'line') = (parent_id IS NULL)),
  CHECK (status <> 'paused' OR kind IN ('line', 'chapter'))
);

CREATE INDEX quests_line_idx     ON quests (line_id);
CREATE INDEX quests_children_idx ON quests (parent_id, position);
CREATE INDEX quests_journal_idx  ON quests (user_id, kind, status);

CREATE TABLE user_settings (
  user_id         text PRIMARY KEY REFERENCES "user"(id) ON DELETE CASCADE,
  active_quest_id uuid REFERENCES quests(id) ON DELETE SET NULL,
  vibration       boolean NOT NULL DEFAULT false,
  sound           boolean NOT NULL DEFAULT false
);
```

Ключевые решения:

- **`line_id` в каждой строке.** Всё дерево цели читается одним простым запросом `WHERE line_id = $1` и собирается в памяти; при росте до 2 000 узлов на пользователя этого хватает с запасом. Рекурсивный `WITH RECURSIVE` остаётся хорошим упражнением, но не нужен на горячем пути.
- **Правила вложенности** (линия → глава или задание, глава → задание, задание → этап) проверяются в сервисе, а не в базе: так проще сообщения об ошибках.
- **Статус хранится у контейнеров тоже**, чтобы фильтры журнала были дешёвым индексным запросом. Он пересчитывается в той же транзакции, что и изменение листа.
- **Порядок — дробный индекс** (строковые ключи библиотеки `fractional-indexing`): перемещение меняет одну строку, без перенумерации соседей.
- **Таблицы авторизации** (`user`, `session`, `account`, `verification`, `rate_limit`) описаны по схеме Better Auth в нашей схеме Drizzle и создаются миграциями drizzle-kit; из личных данных хранятся только email, имя и аватар из Google, а таблица account связывает пользователя с его Google-аккаунтом.

## Доменная логика

Все правила из раздела «Бизнес-логика» PRD — чистые функции пакета `domain`; сервис API лишь загружает дерево линии, вызывает функцию и сохраняет возвращённые изменения в одной транзакции.

```ts
type QuestNode = {
  id: string; parentId: string | null; kind: QuestKind; status: QuestStatus;
  position: string; title: string; deadline: string | null; completedAt: string | null;
};
type Change = { id: string; status: QuestStatus; completedAt: string | null };

buildTree(nodes: QuestNode[]): Tree
progress(tree: Tree, id: string): { done: number; total: number }
applyComplete(tree: Tree, id: string, now: string, opts?: { withChildren?: boolean }): Change[]
applyReopen(tree: Tree, id: string, now: string): Change[]
applyAddChild(tree: Tree, node: QuestNode, now: string): Change[]   // родитель — node.parentId
applyPause / applyResume / applyCancel / applyRestore(tree: Tree, id: string, now: string): Change[]
applyDelete(tree: Tree, id: string, now: string): Change[]          // изменения оставшихся узлов
canBeActive(tree: Tree, questId: string): boolean
nextQuest(tree: Tree, afterQuestId: string): string | null
nextOpenChild(tree: Tree, parentId: string): string | null           // следующий этап для «Сегодня»
suggestQuests(lines: Tree[], limit: number): string[]                // «Выбери квест»: линии в порядке журнала
isBranchLocked(tree: Tree, id: string): boolean                      // предок на паузе или отменён (правило 3)
applyChanges<T extends QuestNode>(nodes: T[], changes: Change[]): T[] // дерево после мутации: сервер и оптимистичный кеш
```

- **`now`** — время в ISO; функции чистые и не читают часы сами. Из него берётся `completedAt` узлов, которые становятся `done`.
- **Ошибки** — исключение `DomainError` с полем `code` (`branch_locked`, `has_open_children`, `invalid_parent`, `invalid_transition`); сервис превращает его в `409`. Повторное действие (отметить выполненное, восстановить неотменённое) не ошибка, а пустой `Change[]`.

### Правила

1. **Прогресс.** Лист — это этап или задание без неотменённых этапов. `progress` = выполненные листья ÷ все листья поддерева; отменённые ветки исключаются целиком, ветки на паузе учитываются.
2. **Подъём статуса.** После любого изменения (отметка, снятие, добавление, пауза, отмена, восстановление, удаление) функция идёт вверх по предкам: контейнер с хотя бы одним неотменённым ребёнком и всеми такими детьми в `done` становится `done`, иначе выполненный контейнер возвращается в `open`. Подъём останавливается на предке на паузе или отменённом — его статус ручной.
3. **Заблокированные ветки.** Если предок узла на паузе или отменён, любое действие с узлом, кроме удаления, отклоняется с `409 branch_locked`. Если на паузе или отменён сам узел, нельзя отмечать, снимать отметку и добавлять в него детей; возобновить, восстановить, отменить узел на паузе и удалить можно. Интерфейс в этих ветках и так делает чекбоксы неактивными.
4. **Задание с открытыми этапами.** Без флага `withChildren` ответ — `409 has_open_children`, и клиент показывает диалог «Отметить все этапы выполненными?»; с флагом закрываются все открытые этапы. Главу и линию вручную можно отметить, только пока в них нет неотменённых детей; иначе — `409 invalid_transition`.
5. **Снятие отметки** с выполненного контейнера возвращает в `open` и его выполненных потомков — иначе подъём статуса сразу закрыл бы его снова. **Возобновление и восстановление** ставят узел в `done`, если все его неотменённые дети выполнены, иначе в `open`; отменённый этап возвращается открытым.
6. **Активный квест.** После каждого изменения сервис проверяет `canBeActive` для `active_quest_id`. Если задание больше не может быть активным, ссылка очищается, а в ответ добавляется предложение `nextQuest`: следующее открытое задание той же главы по порядку, затем первые открытые задания следующих глав, затем задания прямо в линии, затем по кругу с начала линии — так пропущенное открытое задание не теряется. Задания в главах на паузе и отменённых не предлагаются.
7. **Порядок.** Новый элемент получает ключ после последнего «брата», перемещение — ключ между новыми соседями (`generateKeyBetween`). Ключи сравниваются побайтово, как `COLLATE "C"` в базе.
8. **Вставка списка.** Клиент разбирает текст в `QuestDraft` (название и вложенные дети). Вид верхнего уровня задаёт строка «+ Добавить …», куда вставили текст; вложенные уровни выводятся из родителя (глава → задание → этап). Отступы глубже этапа «прижимаются» к этапу, и предпросмотр об этом предупреждает. Разбор — `parseQuestList` в `packages/domain`: отступ — Tab или два пробела, маркеры списков («-», «*», «•», «1.») отбрасываются, названия длиннее 120 символов обрезаются.

### Конкурентность

Каждая мутация — транзакция: `SELECT … FROM quests WHERE id = $lineId FOR UPDATE` блокирует корень линии, затем дерево загружается, домен возвращает `Change[]`, изменения пишутся одним `UPDATE … FROM (VALUES …)`. Так два устройства одного пользователя не могут одновременно сломать каскад в одной цели.

## API

REST под префиксом `/api/v1`, JSON, сессия в cookie; любая мутация статуса возвращает все изменённые узлы, чтобы клиент обновил кэш без повторной загрузки дерева.

| Метод и путь | Что делает | Требование |
| --- | --- | --- |
| `GET /lines?status=open` | Линии статуса с прогрессом, «Главой N из M» (`chapters`) и флагом активного квеста, в порядке журнала; `counts` — число линий в каждом статусе для фильтров | F-14 |
| `POST /lines` | Создать сюжетную линию | F-02 |
| `GET /lines/:id/tree` | Всё дерево линии с прогрессом каждого узла | F-15 |
| `POST /quests` | Создать главу, задание или этап `{ parentId, kind, title, … }` | F-03 |
| `POST /quests/batch` | Создать поддерево из `QuestDraft` `{ parentId, kind, items }` — вставка списка, позже ИИ; не больше 200 элементов | F-03 |
| `PATCH /quests/:id` | Изменить название, описание, дедлайн | F-04 |
| `POST /quests/:id/move` | Новый порядок внутри родителя `{ afterId: string \| null }` (`null` — первым); смена родителя (F-06) — позже | F-05, F-06 |
| `POST /quests/:id/complete` | Отметить; `{ withChildren?: boolean }` | F-08 |
| `POST /quests/:id/reopen` | Снять отметку | F-08 |
| `POST /quests/:id/pause`, `/resume` | Пауза линии или главы | F-09 |
| `POST /quests/:id/cancel`, `/restore` | Отмена и восстановление | F-10 |
| `DELETE /quests/:id` | Удалить узел с потомками безвозвратно | F-07 |
| `GET /today` | Активный квест с путём и этапами, прогресс его линии, другие линии, предложения | F-12, F-13 |
| `PUT /me/active-quest` | Назначить или снять активный квест `{ questId \| null }` | F-12 |
| `GET /me/settings`, `PATCH /me/settings` | Вибрация, звук | — |
| `/api/auth/*` | Вход через Google (редирект и callback), сессия, выход — обработчики Better Auth | F-01 |

### Соглашения

- **Валидация:** тело и параметры каждого запроса проверяются Zod-схемой из `packages/shared`; та же схема типизирует клиент.
- **Ответ мутации:** `{ changed: QuestNode[], activeQuestId: string | null, suggestion?: { id, title } }`; созданный узел тоже входит в `changed`. Если удалили само активное задание, ссылка просто сбрасывается, без предложения; если удаление закрыло активное задание (ушёл его последний открытый этап), предложение есть, как после выполнения.
- **Дерево линии** (`GET /lines/:id/tree`) отдаётся плоским списком узлов с `progress` у каждого — в таком виде его принимает `buildTree` на клиенте.
- **Ошибки:** `{ error: { code, message, details? } }` с HTTP-кодами 400 (`validation_failed`), 401 (`unauthorized`: нет сессии), 403 (`forbidden`: изменяющий запрос с чужого сайта), 404 (`not_found`: нет узла или чужой), 409 (`branch_locked`, `has_open_children`, `invalid_parent`, `invalid_transition`), 413 (`payload_too_large`, тело `POST /quests/batch` больше 128 КБ), 500 (`internal_error`).
- **Чужие данные** всегда отвечают 404, а не 403, чтобы не раскрывать существование чужих id.
- **Идемпотентность:** повторный `complete` уже выполненного узла не ошибка, а пустой `changed` — это важно для повторов из очереди без сети.

## Фронтенд

Серверные данные живут только в кэше TanStack Query, мелкое состояние интерфейса — в Zustand; отметка этапа отображается мгновенно благодаря тому же пакету `domain`, что и на сервере.

### Маршруты

| Путь | Экран | Доступ |
| --- | --- | --- |
| `/login` | Экран входа с кнопкой «Войти через Google» | Без сессии |
| `/today` | «Сегодня» | С сессией |
| `/journal?status=open` | Журнал с фильтром в адресе | С сессией |
| `/line/$lineId` | Сюжетная линия; `?quest=` открывает лист деталей | С сессией |
| `/settings` | Вибрация, звук, выход | С сессией |

Layout `_app` (все экраны, кроме `/login`) проверяет сессию и выбирает раскладку: нижние вкладки на телефоне, три колонки от 1024 px («Сегодня» слева постоянно).

### Данные и кэш

- **Ключи запросов:** `['lines', status]`, `['tree', lineId]`, `['today']`, `['settings']`, `['session']` — в одном файле `shared/api/keys.ts`.
- **Оптимистичная мутация** на примере отметки этапа:
  1. `onMutate` берёт дерево из кэша, вызывает `applyComplete` из `domain` и записывает результат в кэш — прогресс-бары двигаются сразу.
  2. Запрос уходит на сервер; ответ с `changed` заменяет локальный расчёт серверным.
  3. При ошибке кэш откатывается к снимку из `onMutate`, показывается тост «Не удалось сохранить · Повторить».
  4. После успеха инвалидируются `['lines']` и `['today']`.
- **Без сети:** `networkMode: 'offlineFirst'` ставит мутации на паузу и отправляет их при подключении; сохранение очереди между перезапусками (F-19) — позже, через `persistQueryClient` и IndexedDB.
- **Удаление:** диалог подтверждения показывает число потомков; после подтверждения узел убирается из кэша и сразу уходит `DELETE`. Восстановления нет.

### Интерфейс

- **Компоненты по фичам:** `features/line/TreeItem`, `features/today/QuestCard` и так далее; общие примитивы shadcn — в `shared/ui`.
- **Тема:** цвета — CSS-переменные для светлой и тёмной темы, Tailwind ссылается на них; шрифт заголовков подключается локальным файлом woff2.
- **Вибрация:** `navigator.vibrate` только при включённой настройке; в Safari на iOS API нет, там отклик только визуальный.
- **PWA:** vite-plugin-pwa генерирует манифест и сервис-воркер, кэширующий оболочку приложения; API-запросы сервис-воркер не кэширует, этим занимается TanStack Query.

## Авторизация и безопасность

Вход только через Google, сессия в httpOnly-cookie, а каждый запрос к данным ограничен `user_id` из сессии — без исключений.

### Вход

1. На `/login` пользователь нажимает «Войти через Google»; Better Auth перенаправляет его на страницу согласия Google с областями `openid`, `email`, `profile`.
2. Google возвращает его на `/api/auth/callback/google`; Better Auth проверяет ответ, при первом входе создаёт пользователя и связь в `account`, ставит cookie сессии.
3. Клиент перенаправляется на `/today`; при первом входе создаётся строка `user_settings`.

Сессия живёт 30 дней и продлевается при использовании. Приложение запрашивает только имя, email и профиль, поэтому даже в тестовом режиме Google друзей не нужно вносить в список тестировщиков, предупреждение не показывается и вход не истекает через 7 дней. Адрес callback на `*.workers.dev` регистрируется в Google Cloud Console; если Google его не примет, понадобится свой домен, поэтому это проверяем первым делом на этапе 6.

### Безопасность

- **Cookie:** `httpOnly`, `Secure`, `SameSite=Lax`; клиент и API на одном адресе, поэтому cookie обычные, first-party.
- **Изоляция данных:** все репозитории принимают `userId` обязательным параметром; интеграционные тесты проверяют, что чужой id всегда даёт 404.
- **CORS не нужен:** клиент и API на одном origin, запросы с других origin отклоняются: изменяющие запросы к `/api/v1` проверяет `csrf()` из Hono (Origin или Sec-Fetch-Site), `/api/auth` — Better Auth.
- **Ограничение частоты:** встроенный лимит Better Auth на эндпоинтах входа.
- **Секреты** (Google Client ID и Client Secret, строка подключения к базе, секрет Better Auth) — в секретах Worker (`wrangler secret`) и GitHub Actions, не в репозитории.
- **Заголовки:** `secureHeaders` из Hono, Content Security Policy для клиента.

### Аналитика — после MVP

В MVP нет таблицы событий и клиентских событий. Грубую картину для метрик PRD дают уже существующие данные: выполненные элементы за неделю — по `quests.completed_at`, регулярность входов — по `session.updated_at` из таблиц Better Auth; остальное — разговоры с тестерами. Таблица `events` и запись событий появятся после MVP отдельной миграцией.

Два окружения — локальное и продакшен, без staging; продакшен целиком укладывается в бесплатные планы Cloudflare и Neon, а вход через Google бесплатен.

| --- | --- |

### CI/CD (GitHub Actions)

- **На слияние в `main`:** миграции `drizzle-kit migrate` на Neon, затем `wrangler deploy`.
- **Резервные копии:** ежедневный `pg_dump` по расписанию GitHub Actions в артефакты с хранением 14 дней; дополнительно — восстановление на момент времени в пределах окна бесплатного плана Neon.

## Задел для ИИ в v2

В MVP нет ни одного вызова модели, но ИИ-разбиение цели встанет в уже существующий поток без переделок: модель будет генерировать тот же `QuestDraft`, что сейчас получается из вставленного списка.

- **Общий контракт.** Zod-схема `QuestDraft` в `packages/shared` уже описывает дерево черновика; в v2 её же превратим в JSON Schema для structured output модели.
- **Общий путь сохранения.** `POST /quests/batch` и предпросмотр «Будет создано: …» одинаковы для вставки и для ИИ; меняется только источник черновика.
- **Модуль `apps/api/src/ai`.** Все вызовы модели — только с сервера: ключ API не попадает на клиент, а лимиты и затраты считаются в одном месте.
- **Данные для памяти.** Выполненные ветки в `quests` (с `completed_at`) и будущая таблица событий станут контекстом для персональных предложений; pgvector подключается к той же базе Neon отдельной миграцией.
- **Оценка качества.** Набор из 20–30 эталонных целей для evals заводится вместе с первой ИИ-фичей, а не после неё.

## План реализации

Семь этапов до версии для тестеров; каждый заканчивается тем, что можно потрогать руками, а не «написанным слоем».

- [x] **1. Каркас.** Монорепо, docker compose с PostgreSQL, Hono с `GET /health`, Drizzle и первая миграция `quests`, пустое приложение Vite + React + TanStack Router. Готово, когда `pnpm dev` поднимает всё одной командой.
- [x] **2. Домен.** Пакет `domain`: дерево, прогресс, каскады, `nextQuest` — с тестами на каждое правило PRD. Готово, когда все тесты зелёные без базы и браузера.
- [x] **3. API дерева.** Создание, чтение дерева, редактирование, статусы, перемещение, удаление; пока с фиксированным тестовым пользователем. Готово, когда главный сценарий проходит через HTTP-клиент.
- [x] **4. Журнал и экран линии.** Список линий, дерево, «+ Добавить …» с Enter и вставкой списка, отметка с оптимистичным обновлением. Готово, когда автор ведёт в приложении собственную цель.
- [ ] **5. «Сегодня».** Активный квест, следующий этап, предложения после выполнения. Готово, когда автор неделю отмечает этапы только с этого экрана.
- [x] **6. Вход и изоляция.** Better Auth со входом через Google, `user_id` во всех запросах, тесты на чужие данные. Готово, когда два аккаунта не видят данных друг друга.
- [ ] **7. Выпуск.** PWA, деплой на Cloudflare (Hyperdrive создаётся с `--caching-disabled`), резервные копии. Готово, когда первые тестеры установили приложение по ссылке.

После выпуска — требования P1 и P2 (перетаскивание, пауза и отмена, экран завершения), а также Sentry, аналитика событий и e2e-тесты в порядке, который подскажут отзывы.
