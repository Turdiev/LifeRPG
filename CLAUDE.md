# LIFE RPG

PWA-ежедневник, который превращает большую цель в иерархию квестов по образцу RPG:
сюжетная линия → глава → задание → этап. MVP для автора и 5–10 друзей-тестеров.

## Спецификации — источник истины

- `docs/prd.md` — продукт, требования F-01…F-19, бизнес-логика, журнал решений
- `docs/ux.md` — экраны, навигация, состояния, взаимодействия, визуальная основа
- `docs/tech-spec.md` — стек, архитектура, модель данных, API, план реализации

Перед задачей читай нужные разделы. Если код и спецификация расходятся или в спецификации
нет ответа — спроси автора, не меняй поведение и документы молча.

## Режим работы: агент пишет код, автор делает ревью

- Перед крупной задачей (новый этап, новая фича, изменение схемы БД) — короткий план:
  какие файлы, какой подход, какие альтернативы отброшены и почему. Жди подтверждения.
  Мелкие правки делай сразу.
- Делай небольшие, логически цельные изменения, которые удобно ревьюить.
- Только то, что просили: без абстракций под единственный случай, без настраиваемости
  «на будущее», без обработки ошибок для невозможных сценариев.
- Правки точечные: каждая изменённая строка следует из задачи. Соседний код, комментарии
  и форматирование не трогай; заметил проблему рядом — назови её в отчёте, но не чини.
- Формулируй задачу как проверяемую цель: для бага сначала тест, который его воспроизводит,
  потом исправление; у каждого шага плана — своя проверка.
- В задачах по UI используй скилл `frontend-design`: он отвечает за типографику, тексты
  интерфейса, доступность и самопроверку. Визуальное направление задаёт `docs/ux.md` — делай
  по нему, а в отчёте отдельным пунктом пиши, как сделал бы визуал скилл и почему.
- Не делай `git commit` и `git push` — автор коммитит сам после ревью.
- После задачи крупнее мелкой правки, до отчёта, запусти субагента `reviewer`
  (`.claude/agents/reviewer.md`): передай суть задачи и список изменённых файлов.
  Блокеры исправь, остальное реши сам или вынеси автору; итог ревью — отдельным разделом в отчёте.
- После изменений кратко напиши: что сделано, почему так, на что обратить внимание при ревью.
- Объясняй неочевидные решения в React через сравнение с Vue, когда это помогает
  (useEffect vs watch, хуки vs composables и т. п.).
- Отвечай автору по-русски. Код и идентификаторы — на английском; комментарии и сообщения
  коммитов — на русском.

## Актуальная документация библиотек

Не полагайся на память об API библиотек — стек быстро меняется.

- React, TanStack Router/Query, Zustand, Hono, Drizzle, Better Auth, Zod, Tailwind, shadcn/ui,
  vite-plugin-pwa, fractional-indexing — проверяй через MCP-сервер **context7**.
- Cloudflare Workers, wrangler, Hyperdrive, Workers Logs — через MCP-сервер **cloudflare-docs**.

## Стек

TypeScript везде · pnpm workspaces · React + Vite · TanStack Router + Query · Zustand ·
Tailwind + shadcn/ui · Hono на Cloudflare Workers · PostgreSQL (Neon) через Hyperdrive ·
Drizzle ORM · Better Auth (вход через Google) · Zod · Vitest.

## Структура

```
apps/web         React-клиент (PWA)
apps/api         Hono на Workers; один Worker отдаёт статику клиента и /api/*
packages/shared  Zod-схемы запросов и ответов, общие типы
packages/domain  чистая доменная логика: дерево, прогресс, каскады, nextQuest
docs/            спецификации
```

## Команды

Требуются Node ≥ 24, pnpm 11 и Docker Desktop (запущенный).

```
pnpm install            # зависимости всего монорепо
pnpm dev                # PostgreSQL в Docker + wrangler dev (API, :8787) + Vite (клиент, :5173)
pnpm test               # Vitest по всем пакетам; тестам API нужен PostgreSQL (pnpm db:up), база life_rpg_test
pnpm typecheck          # tsc --noEmit в каждом пакете
pnpm lint               # ESLint
pnpm db:up / db:down    # локальный PostgreSQL (docker compose)
pnpm db:generate        # drizzle-kit: новая миграция из apps/api/src/db/schema.ts
pnpm db:migrate         # применить миграции к ЛОКАЛЬНОЙ базе (drizzle.config.ts отказывается работать с не-локальным хостом)
pnpm db:seed            # тестовый пользователь dev-user в локальной базе (до входа через Google, этап 6)
pnpm --filter @life-rpg/api cf-typegen   # перегенерировать worker-configuration.d.ts после правки wrangler.jsonc
```

Компонент shadcn добавляй из `apps/web`: `pnpm dlx shadcn@4.23.0 add <имя>`. CLI сам дописывает в
`package.json` пакеты `cn` и `next-themes` — убери их, а импорт `from "cn"` замени на `@/shared/lib/utils`;
подписи на английском переведи через `src/shared/strings/ru.ts`.

Клиент открывай по `http://127.0.0.1:5173` (Vite слушает IPv4); `/api/*` проксируется на wrangler.

## Архитектурные правила

- `packages/domain` — только чистые функции. Никаких импортов БД, HTTP, React, Workers.
  Каждое правило из раздела «Бизнес-логика» PRD покрыто юнит-тестом; тесты пиши до реализации.
- `packages/shared` — единственный источник контрактов API (Zod); клиент и сервер импортируют оттуда.
- API: маршруты (HTTP, валидация) → сервисы (транзакции, права) → домен → репозитории (Drizzle).
- Каждый репозиторий принимает `userId` обязательным параметром. Чужие данные → 404, не 403.
- Мутации статусов — в транзакции с `SELECT … FOR UPDATE` на корне линии.
- Прогресс никогда не хранится в БД, только вычисляется. Статусы контейнеров хранятся.
- Клиент: серверные данные только в TanStack Query; оптимистичные обновления через функции
  `packages/domain`; Zustand — только для состояния интерфейса.
- Workers: 10 мс CPU на запрос, не Node.js. Node-API — только через `nodejs_compat` и после проверки
  в документации Cloudflare.

## Правила кода

- TypeScript `strict`, без `any`; именованные экспорты.
- Комментарий объясняет «почему», а не «что»: неочевидное решение, ограничение, ссылку на правило PRD.
  Не пересказывай код и не дублируй имя функции; если без комментария код непонятен — сначала
  попробуй переименовать.
- Компоненты React — `PascalCase.tsx`, остальные файлы — `kebab-case.ts`.
- Новая зависимость — только после согласия автора: объясни, зачем она и почему не обойтись без неё.
  Фиксируй точные версии; не бери версии, вышедшие меньше двух недель назад.
- Тексты интерфейса — на русском, в отдельных файлах строк; кавычки «ёлочки», апостроф ’.
- Удаление в приложении безвозвратное и всегда с диалогом подтверждения (решение PRD).

## Безопасность и окружения

- Окружения: локальное (PostgreSQL в Docker, `wrangler dev`) и продакшен. Staging нет.
- Не читай и не выводи `.env*` и `.dev.vars` — секреты задаёт автор сам (`wrangler secret`).
- Миграции и запросы к БД — только к локальной базе. Продакшен меняется только через CI.
- Никогда не запускай `wrangler deploy` и не подключайся к продакшен-базе Neon.
